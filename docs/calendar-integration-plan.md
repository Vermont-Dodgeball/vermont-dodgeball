# Planning: Google Calendar integration

**Status:** draft for discussion — nothing built yet
**Last updated:** 2026-08-11

## Goal

Two things, which are worth keeping separate because they have very different
risk profiles:

1. **Show upcoming game dates on the site**, sourced from a Google Calendar,
   without anyone hand-editing the site when the schedule changes.
2. **Create those calendar events automatically** from an uploaded PDF of a
   venue rental receipt, so booking the gym is the only manual step.

(1) is the original ask and delivers most of the value. (2) is the ambitious
part and is where all the uncertainty lives.

## Where the site is today

- Static HTML on GitHub Pages, no build step, custom domain `vtdodgeball.com`.
- Content lives in `data/about.json` and `data/photos.json`, fetched
  client-side and rendered by inline JS.
- Sveltia CMS at `/admin/` commits directly to `main`; a Cloudflare Worker
  (`sveltia-cms-auth`) handles the GitHub OAuth exchange.
- The homepage already has a **"Next Game" card** (`nextGame` in
  `data/about.json`) with when/where/cost. It is currently CMS-edited by hand.
  **This is the slot the calendar data drops into** — the markup and styling
  already exist.

Everything is free: GitHub Pages hosting, Cloudflare Workers free tier,
unlimited Actions minutes on public repos.

## Feasibility assessment

| Component | Rating | Why |
| --- | --- | --- |
| Display events from a Google Calendar | **High** | Public calendar + free API key, read directly from browser JS. No server, no build step. Well-trodden. |
| Write events to Google Calendar | **High** | A service account with the calendar shared to it can create events. Free. Needs somewhere to hold a secret key — we already run a Worker, and Actions secrets are another option. |
| Extract structured data from a receipt PDF | **Medium** | Entirely dependent on the receipt's format — see Open Questions. A text-based PDF from booking software is very tractable; a scanned image is a different problem. |
| **Fully automatic, no human review** | **Medium** | The mechanics are all solid. The risk is that a parsing mistake silently creates wrong events on a calendar people rely on. Mitigated by design (see Option B). |

**Overall: feasible, and I'd rate it "worth doing" — but not as one big
automatic pipeline.** The honest framing is that the *plumbing* is easy and
free; the *parsing* is the only real unknown, and it's an unknown I can't
resolve without seeing an actual receipt.

## The blocking question: what does the receipt look like?

Everything about Phase 2 depends on this, so it's worth answering before
designing further:

1. **Is the PDF text-based or a scan?** Selectable text (generated by the rec
   center's booking system) means deterministic parsing and near-perfect
   reliability. A scanned/photographed page needs OCR or a vision model, and
   accuracy drops.
2. **Does one receipt cover one booking or a whole season?** A receipt listing
   "Mondays, Sept 8 – Dec 15" needs date expansion; one listing each session
   explicitly is simpler.
3. **How consistent is the format between receipts?** If the rec center's
   system emits the same layout every time, a regex parser is reliable and
   free forever.
4. **How often does this happen?** Once a season? Monthly? This decides whether
   automation is worth building at all versus just typing dates into the CMS.

work starts.**

## Proposed architecture

### Phase 1 — Display events from the calendar (low risk, do this first)

The homepage fetches upcoming events from a **public** Google Calendar and
renders them into the existing Next Game card.

- Make the league calendar public (it likely already should be — people want
  to subscribe to it).
- Create a Google Cloud project, enable the Calendar API, generate an **API
  key restricted by HTTP referrer** to `vtdodgeball.com`. Free tier;
  the quota is far beyond anything this site will use.
- Add a `<script>` that calls the events endpoint for the calendar, takes the
  next N upcoming events, and fills in the card. Fall back to the existing
  static `nextGame` values in `data/about.json` if the request fails — so the
  card degrades to today's behavior rather than going blank.

Notes:
- The API key is *public* by necessity (it ships in the page). Referrer
  restriction is the control; the key only grants read access to a calendar
  that is already public, so exposure is not a real risk.
- Data refreshes on every page load — better than the "refresh when an event
  changes" bar from the original ask.
- **This phase has no dependency on Phase 2** and delivers the headline
  feature on its own.

### Phase 2 — Create events from a receipt PDF

Three sub-problems: getting the PDF somewhere, reading it, and writing events.

**Upload.** Reuse the CMS. Sveltia can upload files to a repo folder
(`assets/receipts/` or similar), which means a commit lands in the repo with
no new infrastructure and no new login for anyone to learn.

**Trigger.** That commit fires a GitHub Actions workflow (free on public
repos) scoped to the receipts path.

**Parse.** Two candidate approaches, not mutually exclusive:

- *Deterministic:* extract text (`pdftotext`, `pdfplumber`) and match with
  regex. Free, fast, fully predictable, and easy to unit-test against saved
  sample receipts. **Preferred if the format is consistent.**
- *Model-based:* send the PDF to the Claude API, which accepts PDFs directly
  as a document content block, and use **structured outputs** to force a
  response matching a fixed JSON schema (dates, times, venue, cost). Handles
  layout variation and messy scans that regex can't.

  On cost: this is a genuinely tiny workload. A one- or two-page receipt is on
  the order of a couple thousand input tokens. At Claude Haiku 4.5 rates
  (\$1 per million input tokens) that's a fraction of a cent per receipt;
  even on Claude Opus 5 (\$5/M) it's about a penny. At a handful of receipts
  per season this is **cents per year, not dollars** — but it is not
  *literally* free, and it needs an API key, so it's your call whether that
  crosses the "no budget" line. Prices here are from my reference data and
  worth confirming before committing.

  Practical suggestion: **try deterministic parsing first**, and keep the
  model-based path as the fallback for receipts the parser can't handle.

**Write.** A Google Cloud **service account** with the calendar shared to it
(with "Make changes to events" permission) can create events via the API. The
service account's JSON key lives in an Actions secret. No OAuth dance, no
token refresh, no per-user consent — this is much simpler than user OAuth for
an unattended job.

**Idempotency matters here.** Re-running the workflow, or re-uploading the
same receipt, must not create duplicate events. The Calendar API lets you
specify your own event ID on insert, so deriving a deterministic ID from
(receipt identifier + event date) makes repeat runs harmless — a re-run
updates the existing event instead of adding a second one. Note the API
constrains the ID character set (base32hex-style: lowercase `a`–`v` and
digits), so IDs need hashing/encoding rather than raw strings.

### Option A vs Option B: how much human review?

**Option A — fully automatic.** Upload → parse → events appear on the
calendar. Fewest steps. Risk: a parsing error silently publishes wrong dates
to a calendar members trust, and nobody notices until people show up on the
wrong night.

**Option B — human-in-the-loop (recommended).** Upload → parse → the workflow
**opens a pull request** containing the proposed events as a data file → you
glance at it and merge → merging creates the calendar events. Costs one click.
Buys a review step exactly where the fragility is, using the Git workflow
that's already in place. If the parser is wrong, the PR is just closed and
nothing was published.

I'd start with B. If it proves reliable after a season, collapsing it to A is
a small change.

## Suggested sequencing

1. **Phase 1** — calendar → site. Independent, low risk, delivers the main
   value. Ship this first regardless of what happens with Phase 2.
2. **Collect a sample receipt** and answer the Open Questions.
3. **Phase 2a** — parser only, run manually, output checked by eye against
   real receipts. No calendar writes yet.
4. **Phase 2b** — wire up the Action + service account with the PR review step
   (Option B).
5. **Optional** — drop the review step once it's earned trust.

## Risks and things that could go wrong

- **Receipt format changes.** The rec center updates its booking software and
  the regex silently stops matching. Mitigation: the workflow should fail
  loudly (a failed Action emails you) rather than producing an empty result.
- **Wrong dates published.** Addressed by Option B's review step.
- **Service account key leakage.** It only has access to the one calendar it's
  been shared with; scope it to that and nothing else. Never commit the key.
- **Google Cloud project quotas/billing.** The read path is free-tier. Confirm
  no billing account is required for Calendar API usage at this volume before
  relying on it.
- **Timezone handling.** Games are US/Eastern; naive date parsing plus DST is
  a classic source of off-by-one-hour bugs. Use explicit timezone-aware
  timestamps when creating events.
- **Automation for its own sake.** If this happens twice a season, typing four
  dates into the CMS takes two minutes. Phase 2 is worth building if it's
  frequent or error-prone, and probably isn't if it isn't. Phase 1 is worth it
  either way.
